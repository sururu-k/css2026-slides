イーサリアムの多実装環境とファイナリティ

背景・問題意識
イーサリアムとは
分散型のブロックチェーンプラットフォーム。
「公式ソフト」が存在しない
共通の仕様書をもとに、複数の開発チームが別々の言語でノード（クライアント）を開発・運用。
Go Rust Java C# TS
ファイナリティとは
「一度確定した取引は絶対に覆らない」という性質。崩れると確定した取引が消えたり二重支払いが起きたりする。
本研究の問い
各クライアントを「仕様通り」に作っていれば、ファイナリティは本当に安全と言い切れるか？
共通の仕様書から様々な言語でクライアントが作られている

Casper FFG と安全性の仕組み

違反者を特定できる安全性
Casper FFG（投票で確定を決める仕組み）
参加者（検証者）が投票し、全体の 2/3 以上の投票が集まると「確定（Finalized）」。
違反者を特定できる安全性（Accountable Safety）
「もし間違って2つのブロックが同時に確定しても、両方に投票した違反者を特定して資産を没収（スラッシュ）できる」という証明。
なぜ安全と言えるか（投票の重なり）
2/3以上の集団が2つあれば、算術上（2/3 + 2/3 = 4/3 > 1）必ず 1/3 以上が重なる。
前提条件
「重なった違反者が実際に検出・処罰される」という前提があって初めて安全と言える。
2つの2/3投票は必ず重なり、二重投票者を特定して没収できる

イーサリアムの「仕様書」とは何か

EIP & Executable Spec
イーサリアムの仕様書（consensus-specs / EIP）
英語の説明文 ＋ 実際に動かせる Python テストコード で標準化。
仕様書の役割
各クライアントが同じ順序で処理を行うための「手順」を定めること。
仕様書に書かれていないこと
1ステップごとの処理ロジックは詳しいが、「なぜこれで安全と言えるのか（証明が前提にしている全体ルール）」は書かれていない。
課題
仕様書だけを見て行う監査では、証明の前提条件が守られているか確認しにくい。
仕様書は手順コードを持つが、安全のための全体ルールは書かれていない

形式証明からの前提条件の取り出し

Lean 4 による自動取り出し
出発点: Lean 4 での証明
Casper FFGの安全性をLean 4で検証した17個の定理を利用。
前提条件の取り出し
Leanの定理の型（引数）から「実装が満たすべき前提」をそのまま取り出す。
具体例 (CHK-GEN-09)
主定理の前提 `¬q_intersection_slashed`（重なった二重投票者が未処罰で残らないこと）を特定。
自動処理による抽出
LLMを使わないプログラム処理のため、嘘や勝手な前提の混入なしに 延べ57件 の前提を取り出した。
Lean 4の定理の型から前提条件を取り出し、仕様書を検索

仕様書との照合方法

判定基準と判定器
対象
仕様書 `consensus-specs` の全 89 Markdown ファイル。
判定基準
・明示あり（E）: 仕様書の文章に安全上の要件として書かれている
・明示なし（非E）: 仕様書の文章に要件として書かれていない
判定方法
キーワード検索器 1 種 ＋ 6 種類の LLM （計 7 つの判定器）で自動判定。
分析の範囲
「仕様書の文章に要件として明記されているかどうか」を評価。

照合の手順

1. Lean 4 の証明から前提条件を取り出す [57件]

2. 仕様書（89ファイル）を検索

3. 7つの判定器で二値判定（E / 非E）

4. 結果を数値化

結果：前提の84%は仕様書に書かれていない

分析結果
結果
57件中 48件（84.2%） が7つの判定すべてで 「書かれていない（非E）」。
全員一致で「書かれている」
7つの判定器全員が「書かれている」とした前提条件は 0件。
「関数の動き」と「全体のルール」の違い
仕様書: `is_slashable_attestation_data`（同じエポックで2回投票したらスラッシュ処理する）
証明の前提: `q_intersection_slashed`（重なった二重投票者が未処罰で残ることはない）
分かったこと
仕様書は手続きの指示にとどまり、安全のための前提条件が書かれていないことが数値で確認できた。
57前提中48件(84.2%)が未記載／関数の動きと全体ルールの違い

結果の読み方

結果の補足と課題
「セキュリティの話が全くない」訳ではない
・`weak-subjectivity.md`: スラッシングの閾値など、安全性の結果について大まかに解説している。
本研究で分かったこと
大まかな解説や個別のコードはあるが、開発者や監査者がテストで確認できる「具体的な要件」の形では書かれていない。
仕様書だけを見る監査の課題
大域的な前提条件が要件として書かれていないため、仕様書だけを見る監査で見落としが生じやすくなる。

差分のポイント

「大まかな解説」 vs 「検証できる具体要件」

手順の説明だけでは証明の前提条件が網羅されないため、監査のすり抜けが起きる可能性がある。

過去のバグ発生場所との一致

実際のバグ例
分かったこと
仕様書で前提が書かれていなかった「正当化・確定処理」の場所で、過去に実際のバグが起きていた。
Nimbus PR#461（チェーン分岐発生）
正当化フラグの計算ミス（整数オーバーフロー）で確定の判定がズレ、実際にネットワークが分裂。
Lighthouse PR#4576（確定計算の不整合）
エポック境界の処理バグにより確定計算が食い違った。計算ロジック修正で対応。
まとめ
仕様書に前提条件が書かれていない部分は、コードを書く際にバグを作り込みやすい場所と言える。
前提が書かれていない場所で過去に実際にチェーン分岐バグが発生

提案: 実装する人と仕様書を書く人はどうすべきか

実務への提案
クライアントを実装する人へ
1. 仕様コードの丸写しをしない: 前提ルールが壊れていないか確認するコード（アサーション）を自前で入れておく。
2. 57個の前提リストの活用: 自動テスト（ファジング）やコード確認のチェックリストとして使う。
仕様書を書く人（EIP著者）へ
1. 前提条件を文章で追記する: Pythonコードだけでなく、「前提としているルール」を文章として仕様書に書く。
2. 証明（Lean/Coq）と紐づける: 証明の前提と仕様記述をリンクさせ、第三者が確認できるようにしておく。
実装する人・仕様書を書く人それぞれのアクションプラン
