確定（ファイナリティ）とは何か

Casper FFG
05 / 13
ファイナリティ（Finality）の保証
「一度確定した取引や状態は、将来絶対に覆らない」という合意保証。
もし確定が覆ると、決済完了後に送金が消失する「二重支払い攻撃」が成立してしまいます。
Casper FFG の確定ルール
参加者（バリデータ）がチェックポイントへ投票し、全体の 2/3 以上のステーク投票が集まったときに「確定（Justified / Finalized）」と判定されます。
数学的に証明された安全の仕組み
万が一、競合する2つの異なる状態が同時に確定するような事故が起きても、「両方に二重投票した不正者を必ず特定し、彼らが預託した資産を没収（スラッシング）できる」ことが数学的に証明されています。

不正の被害コストが攻撃利益を確実に上回るため、合理的に攻撃を防げる設計です。

なぜ 2/3 の投票で安全と言えるのか？

算術的根拠と前提
06 / 13
投票の算術的な重なり
2/3 ＋ 2/3 ＝ 4/3 ＞ 1
2つの競合する決定が同時に確定した場合、計算上必ず全体の 1/3 以上の参加者が二重投票の不正を行っていることになります。
見落とされがちな「暗黙の前提条件」
「二重投票した不正者が、実際のプログラム上で確実に検出・集計され、処分（没収）が完了していること」
数学的証明は「この前提条件がコードでも正しく守られている」という仮定の上に成り立っています。もしコード上の不備で不正者の処分が漏れれば、証明の保証は崩壊します。

仕様書（consensus-specs）の中身と限界

仕様書の実態
07 / 13
仕様書の構成
仕様書は、英語の解説文と、実際に動作する Python 実装例（テストコード） で構成されています。各開発チームはこのコードを手本にして自言語へ移植します。
仕様書の根本的な限界
✔ 書かれていること：ステップごとの「計算手順」（How）
✘ 書かれていないこと：「なぜ安全か」「証明が前提とする全体ルール」（Why）
consensus-specs / justification.py Python 
# 仕様書にある実装例（計算手順）
def process_justification(state):
    if matching_target_balance * 3 >= total_active_balance * 2:
        state.current_justified_checkpoint = ...

# ⚠️ 手順は明記されているが、
# 「不正者の処分が未完了のまま確定してはならない」
# という証明の前提ルールはコードに一切現れない！

対策：自動テストでのチェック（アサーション）

防衛策の提示
08 / 13
アサーション（Assertion）とは
テスト実行中やプログラム内で「この時点で絶対にこのルールが成り立っていなければ異常である」という前提条件を自動検証するチェックコード。
なぜアサーションが必要か
仕様書の実装例には手順しかなく、前提検証がありません。
開発者が「全体ルールが崩れていないか」を確認するアサーションを自前のテストケースに仕込むことで、移植時に生じるロジックバグを自動検出できます。
テストコードでの比較検証例 Python 
# ✘ 仕様書の丸写し移植（危険）
def process_justification(state):
    if votes * 3 >= total * 2:
        state.checkpoint = ...

# ✔ アサーションを追加した安全設計
def process_justification(state):
    if votes * 3 >= total * 2:
        state.checkpoint = ...
        assert no_unprocessed_slashings(state)
        assert bits_count_valid(state)

Nimbus PR#461（チェーン分裂障害）
障害事象：バリデータ集合のビット計算ミスにより確定判定が他クライアントとズレ、本番ネットワークが実際に2つに分裂！

普遍的セキュリティ課題

なぜイーサリアムで最初に起きたのか？
イーサリアムが「単一の公式実装を持たず、共通仕様書から多様な言語へ移植開発される」という過酷なマルチ実装環境だったため、この問題がバグとして最も早く可視化されたに過ぎません。
一般システム共通のセキュリティ問題
仕様の実装例を別言語や自社環境へ移植する際、モデルの暗黙前提が壊れてバグ化するリスクは、以下の領域すべてに共通します：

・分散合意アルゴリズム（Raft, Paxos）
・金融決済・通信規約（ISO 20022, FIX）
・OS・ネットワークプロトコル（POSIX, BGP, TLS）

まとめと今後の設計指針

総括
13 / 13
本研究の成果
形式証明（Lean 4）から 57 件の安全前提を機械抽出し、84.2% が仕様書に書かれていないことを定量的に証明。さらに、それらの未記載領域が過去の実際のネットワーク分裂バグの根本原因となっていたことを実証しました。
明日から使える 3 つの設計・検証指針
1. 仕様コードの丸写しを脱却する：計算手順（How）だけでなく、安全理由（Why）を意識した設計を行う
2. 大域前提をアサーションで常時監視する：自分のテストスイートに不変条件チェックを自前で組み込む
3. 57 件のチェックリストを活用する：仕様書依存を脱し、監査・ファジングテストの網羅性を劇的に向上させる
