イーサリアムとは何か？〜公式ソフトのない「多実装環境」〜

背景・基本概念
イーサリアムとは
分散型のブロックチェーンプラットフォーム。
なぜ「公式ソフト」が存在しないのか
単一障害点（1つのソフトのバグで全停止）を防ぐため。共通の仕様書のもと、多様な言語で開発・運用。
Go Rust Java C# TS
ファイナリティ（Finality）とは
「一度確定した取引は絶対に覆らない」という性質。崩れると確定した取引が消えて二重支払いが起きる。
本研究の問い
各チームが仕様書どおりにクライアントを作っていれば、ファイナリティは本当に安全と言えるか？
共通仕様書から主要言語・クライアント（実行層/合意層）が分岐する全景

安全性の定理と「なぜ安全と言えるのか」

違反者を特定できる安全性
Casper FFG（投票で確定を決める仕組み）
検証者が投票し、全体の 2/3 以上（Quorum）の投票が集まると「確定（Finalized）」。
違反者を特定できる安全性（Accountable Safety）
「もし間違って2つのブロックが同時に確定しても、両方に投票した違反者を特定して資産を没収（スラッシュ）できる」という証明。
なぜ安全と言えるか（算術的な重なり）
2/3以上の集団が2つあれば、算術上（2/3 + 2/3 = 4/3 > 1）必ず 1/3 以上が重なる（二重投票者）。
前提条件（Assumption）
「重なった違反者が実際にシステムで検出・処罰される」という前提があって初めて保証される。
2つの2/3クオラムは必ず重なり、二重投票者を特定して没収できる

イーサリアムの「仕様書」とは何か

EIP & Executable Spec
イーサリアムの仕様書（EIP / consensus-specs）
英語の記述 ＋ 実際に動く Python テストコード （Executable Spec）で構成。
仕様書の役割
各クライアントが同じ順序で処理を行うための「1ステップごとの手順」を定める。
仕様書に書かれていないこと
手順コードはあるが、「なぜこれで安全と言えるのか（証明が前提にしている全体ルール）」は書かれていない。
課題
仕様書の手順コードだけを見る監査では、証明の前提条件が守られているか確認しにくい。
EIP文章・Python手順コードと、抜けている全体安全ルールの対比

形式証明からの前提条件（Assumption）抽出

Lean 4 による自動抽出
出発点: Lean 4 での形式証明
Casper FFGの安全性をLean 4で検証した17個の定理を利用。
前提条件の機械的取り出し
Lean定理の型（引数）から「仮定（Premise）」をプログラム処理でそのまま抽出。
具体例 (CHK-GEN-09)
主定理の前提 `¬ q_intersection_slashed`（重なった二重投票者が未処罰で残らないこと）を特定。
抽出結果
LLMを使わないプログラム処理により、嘘なしに 延べ 57 件 の前提条件を取り出した。
Lean 4の型情報から前提条件を取り出し、仕様書を検索する流れ

調査方法：仕様書との照合

判定基準と判定器

照合対象

仕様書 `consensus-specs`
全 89 Markdown ファイル

二値判定基準

・明示あり（E）:
仕様書内に要件として文章記述がある

・明示なし（非E）:
仕様書内に要件として書かれていない

7つの判定器

・キーワード検索器 (1種)
・LLM によるクロス検証 (6種)

仕様書から安全前提を読み取れるかを客観評価

結果：前提の 84.2% は仕様書に書かれていない

分析結果
未記載率 84.2%
57件中 48件（84.2%） が7つの判定すべてで 「書かれていない（非E）」。
全員一致で「書かれている」判定
7つの判定器全員が「書かれている」とした前提条件は 0件。
仕様書の文章例 vs 証明の前提
・仕様書: `is_slashable_attestation_data`（同じエポックで2回投票したらスラッシュ処理する）
・証明前提: `q_intersection_slashed`（重なった二重投票者が未処罰で残ることはない）
本質的な差分
仕様書は手続きの指示にとどまり、安全のための全体前提条件が書かれていない。
57前提中48件(84.2%)が未記載／関数の動きと全体ルールの対比

結果の補足と仕様書監査の課題

結果の読み方
セキュリティの記述が「全くない」訳ではない
`weak-subjectivity.md` などでスラッシング閾値の大まかな記述や概念説明は存在する。
本研究で分かったこと
大まかな解説や手順コードはあるが、開発者や監査者がテストで確認できる「明示的な要件」の形になっていない。
仕様書監査の限界
自然言語と手順コードだけの仕様書に依存した監査では、証明の前提条件のすり抜けを防止できない。

ギャップの本質

「大まかな解説」 vs 「検証できる具体要件」

手順のなぞり書きだけでは証明の前提条件が網羅されないため、監査のすり抜けが生じる。

仕様未記載領域と実際のクライアントバグの一致

実際の障害バグ例
核心的発見
仕様書で前提が書かれていなかった「正当化・確定処理」の領域で、過去に実際の重大なバグが起きていた。
Nimbus PR#461（チェーン分岐障害）
正当化フラグ計算の整数オーバーフローにより確定判定がズレ、ネットワークが実際に分裂。修正: ビット計算のアサーション追加。
Lighthouse PR#4576（確定計算の不整合）
エポック境界の処理バグにより確定計算が食い違った。修正: 確定計算ロジック修正。
結論
前提条件が未明記の領域は、実装者がバグを作り込みやすい危険地帯となっている。
前提未記載領域で過去に実際にチェーン分岐障害が発生

実務への提案：実装者と仕様執筆者は何をすべきか

実務アクションプラン
1. クライアントを実装する人へ
・仕様コードの丸写しをしない: 手順通り動かすだけでなく、`q_intersection_slashed` などの前提が壊れていないか確認するアサーションを自前で挿入。
・57個の前提リストの活用: ファジング（自動テスト）やコード確認のチェックリストとして運用。
2. 仕様書を書く人（EIP著者）へ
・大域的な前提条件を文章で明記する: Pythonコードだけでなく「前提とするルール」を文章化。
・形式証明（Lean/Coq）と紐づける: 証明の前提と仕様記述を相互リンクし、監査性を高める。
