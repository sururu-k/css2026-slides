核心の問い

「各クライアントを仕様書通りに作っていれば、本当に安全と言い切れるのか？」

背景：イーサリアムの「多実装環境」
単一の公式ソフトが存在せず、世界中の独立チームが Go, Rust, Java など多様な言語で開発・運用。

確定（ファイナリティ）の仕組み

Casper FFG
ファイナリティ

Casper FFG
検証者が投票し、全体の 2/3 以上 の投票が集まると「確定」。

安全性の証明（Accountable Safety）

万が一2つのブロックが同時に確定しても、両方に投票した違反者を特定して資産を没収（スラッシュ）できる。

見落とされがちな「前提条件」

隠された前提

算術的な重なり

2/3 ＋ 2/3 ＝ 4/3 ＞ 1

2つの確定があれば必ず 1/3 以上が重複（二重投票者）

隠れた前提条件（Assumption）

「重なった違反者がシステム上で確実に検出・処罰される」

※ この前提が守られて初めて安全性が成立する

EIP & Code

仕様書の限界
・書いてあること: 各ステップの計算手順（How）
・書かれていないこと: 証明が前提にする全体ルール（Why）
if matching_target_balance * 3 >= total_active_balance * 2:

# 手順はあるが「全体安全ルール」は未記載

対策の鍵：「アサーション」とは

用語解説

アサーション（Assertion）

「この時点で絶対にこのルールが成り立っていなければおかしい」という前提を自動チェックする安全装置

例え
飛行機の「高度がマイナスになったら自動で緊急ブレーキを引く」メカニズム。
必要な対策
仕様書コードにない前提確認アサーションを、自前コードに仕込むこと！
