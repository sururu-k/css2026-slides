問いと背景
「仕様書通りに実装すれば、本当に安全か？」
多実装環境（Ethereum の例）

Go・Rust・Java・C# など 複数チームが独立して同一仕様を実装。
全実装が仕様書に従っていても、実際にバグが発生した。

実装クライアント例:
go-ethereum Lighthouse (Rust) Prysm (Go) Nimbus (Nim) Teku (Java) Lodestar (TS)
💥 仕様書に従っていても
安全性の証明が前提とするルールが実装から抜け落ちる

4 / 13
確定（ファイナリティ）とは
「一度決まった取引は絶対に覆らない」
ファイナリティの定義

ブロックチェーン上のある状態が 永続的に確定 し、
後から覆されないことの保証。

💸 崩れると

二重支払い攻撃が成立する。
同一コインを複数回使用できる致命的な脆弱性。

✅ Casper FFG の仕組み
  • バリデータの 2/3 以上が投票 → 確定
  • Supermajority Link（スーパーマジョリティリンク）
  • Checkpoint 間のリンクで連鎖的に確定
🛡 安全保証

不正に 両方のブランチに投票した者（スラッシャブル）を
検出し、デポジットを没収（スラッシング）できる。
→ 不正コストが収益を超える設計

5 / 13
なぜ 2/3 で安全か
算術と「隠れた前提」
📐 算術
2/3 ＋ 2/3 ＝ 4/3 ＞ 1
↓
1/3 以上が必ず二重投票
2つの競合するブランチそれぞれに 2/3 が投票したなら、 少なくとも 1/3 が両方に投票していることになる。
⚠️ 隠れた前提（証明が依存するルール）
  • 二重投票者が コード上で確実に検出 される
  • スラッシング処理が 確定より前に完了 している
  • ビット計算・バリデータ集合が 一貫して管理 されている
これらの前提が成り立ってはじめて
「2/3 で安全」という証明が有効になる。
前提が抜けると証明は成立しない。
6 / 13
仕様書の限界
How は書いてある。Why は書かれていない。
仕様書に書いてあること
  • How（計算手順）: 票数の比較、チェックポイントの更新方法
  • 関数シグネチャとPython実装例
  • 個別ルールのエラー検査
仕様書に書かれていないこと
  • Why（なぜ安全か）: 証明が依存する全体ルール
  • 処理の順序制約（スラッシング先行など）
  • 複数関数にまたがるグローバル不変条件
consensus-specs の実装例（一部）
# consensus-specs の実装例
if matching_target_balance * 3 >= \
        total_active_balance * 2:
    state.current_justified_checkpoint = \
        ffg_checkpoint

# 手順はある。
# しかし「全体ルール」は書かれていない。
↑ このコードだけでは、
スラッシング処理の完了タイミングや
バリデータ集合の一貫性は検証されない。
7 / 13
対策：アサーション
「この時点でこのルールが成り立っているはず」を自動検証する
✗ Before（仕様書の実装例のみ）
# 仕様書の実装例
def process_justification(state):
    if votes * 3 >= total * 2:
        state.checkpoint = ...

    # 全体ルールの確認なし
    # 前提チェックなし
手順は正しくても、証明が前提とする
グローバル不変条件が満たされているか不明。
✓ After（アサーション追加）
# アサーションを追加
def process_justification(state):
    if votes * 3 >= total * 2:
        state.checkpoint = ...
        assert no_unprocessed_slashings(state)
        assert bits_count_valid(state)

    # ↑ 全体ルール確認
    # ↑ 前提チェック
証明が前提とする条件を実行時に明示検証。
バグは「壊れた不変条件」として即座に検出される。

実際のバグ事例
仕様書に書かれていない全体ルールの見落とし
Nimbus PR #461
ビット計算ミス ネットワーク分裂
現象: バリデータ集合のビット演算誤りにより
ネットワークが 2分裂。異なるブランチが確定。
根本原因: 「ビット数が常に一致していること」という
グローバル不変条件が未検査。
修正: アサーションを追加し不変条件を常時検証。
Lighthouse PR #4576
確定計算不整合 ロジックエラー
現象: ファイナリティ計算の内部状態が
チェックポイント間で不整合。
根本原因: 「確定前にスラッシング処理が完了していること」
という順序制約が仕様書に未記載。
修正: 処理順序を明示したロジック修正。
共通点: 両バグとも「仕様書に書かれていない全体ルール」の見落としが根本原因。 個別の手順実装は正しかった。

Web3 だけではない
多実装プロトコル全般に存在する問題
なぜ Ethereum で先に表面化したか
  • 公式実装なし: 仕様書が唯一の権威
  • 多言語移植: 6チームが独立して実装
  • 高い経済インセンティブ: バグが即座に顕在化
  • 透明性: PR・バグ報告が公開されている
同じ問題がありうる領域
分散合意アルゴリズム: Raft / Paxos の多実装環境
金融決済システム: ISO 20022 / FIX プロトコルの実装差異
OS・カーネル: POSIX 準拠実装間の挙動差
ネットワークプロトコル: TLS / BGP の実装間不整合
教訓: 仕様書の品質を上げるだけでは不十分。 安全性の証明が前提とするルールを、 実装側でアサーションとして明示する習慣が必要。
