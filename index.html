本日の問いと「公式ソフトがない仕組み」

問題意識

核心の問い

「みんなが仕様書通りに作っていれば、本当に安全と言いきれるのか？」

背景：イーサリアムの「公式ソフトがない仕組み（多実装環境）」
1つのソフトのバグで全体が止まるのを防ぐため、共通仕様書をもとに Go, Rust, Java など別々の言語で開発・運用。

実践ケーススタディ：なぜイーサリアムなのか？

検証の具象例

世界最大の「多実装分散プロトコル」でのケーススタディ

本研究では、確定（ファイナリティ）の仕組みを世界最大規模で実践運用している イーサリアムを具象例（ケーススタディ） として検証を行いました。

ここからの解説前提

以降で解説する確定ルールや仕様構造は、イーサリアムのコンセンサス層（Casper FFG）の具体仕様をもとに進めます。

取引が確定する（ファイナリティ）ルール

Casper FFG
ファイナリティ
「一度決まった取引は絶対に覆らない」という保証。
Casper FFG
参加者が投票し、全体の 2/3 以上の投票 が集まると「確定」。

違反者を没収できる安全の仕組み

万が一2つの取引が同時に確定しても、両方に投票したズルい違反者を特定して預託資産を没収できる。

なぜ 2/3 の投票で安全と言えるのか？

わかりやすい解説

投票の算術的な重なり

2/3 ＋ 2/3 ＝ 4/3 ＞ 1

2つの確定があれば必ず 1/3 以上が二重投票のズルをしている

隠された前提条件

「重なったズルい違反者が、コード上で確実に自動検出されて処分（没収）される」

※ この前提がコードで守られていて初めて安全と言える！

本質的考察

なぜ Web3（イーサリアム）だったのか？

「公式ソフトがなく、共通仕様を多様な言語に丸写し移植する」という環境だったため、最初にバグとして問題が表面化しただけ。

本質：あらゆる分散システム・プロトコル共通の課題

仕様を他言語へ移植する際、モデルの暗黙前提が壊れる問題は、Raft / Paxos / 金融決済 / OS / ネットワークプロトコル全般共通の課題！
